# Beemuu forward roadmap — v3.8.0 → v5.0.0

**Status:** active. Written 2026-10-15, immediately after the v3.7.0 release.
**Scope:** seven cycles, v3.8.0 through v5.0.0. Every slice below is **Tier A**
(pure analysis over logs/snapshots/community data, plus webview UI and docs) —
no new transport, no ECU reads, no writes, so the whole arc lands without a
human merge.

This is the schedule of record. Per-cycle plan docs
(`docs/vX.Y.0_plan.md`) carry the slice detail; `ROADMAP.md` carries the
canonical table.

---

## Why this arc

v3.0.0 shipped ten forensic engines ("The Car Remembers"). v3.1–v3.7 wired the
panels, the maintenance/dossier flow, the registry integrity work and the
app-shell polish. Two things are still open and define the next two major
bumps:

1. **Analysis that reads *relationships* rather than single signals.** The v3
   engines each look at one channel (misfires, drift, cold start). The three
   most valuable unbuilt features are cross-signal — signal integrity, drive
   cycles, and physical plausibility between sensors.
2. **The plugin ecosystem (VISION.md Phase 1).** Package API 2 and the
   community registry shipped; the **capability bridge is the remaining piece**
   and is explicitly "unbuilt work, not deferred work" in `ROADMAP.md`. It is
   the single feature that makes v5.0.0 a major version rather than another
   point release.

## The map

| Cycle | Codename | Tier | Headline slice | Module |
|-------|----------|------|----------------|--------|
| v3.8.0 | Signal Integrity | A | Per-signal health scoring — stuck/flatline, dropouts, noise, implausible steps | `src/js/signal_quality.js` |
| v3.9.0 | Drive Cycle Analyst | A | Segment a log into drive cycles and score each (idle ratio, cold start, warm-up, regen candidates) | `src/js/drive_cycle.js` |
| v4.0.0 | The Fleet | A | Garage-scale fleet health board — per-vehicle grade, overdue/due-soon, cost totals, cross-vehicle ranking | `src/js/fleet_dashboard.js` |
| v4.1.0 | Provenance | A | Is a service history plausible? Odometer monotonicity, back-dating, duplicates, cost outliers | `src/js/service_provenance.js` |
| v4.2.0 | Cross-Check | A | Physical-relationship checks between sensor pairs — which side of the pair is lying | `src/js/sensor_plausibility.js` |
| v4.3.0 | Second Opinion | A | Weighted consensus over community repair opinions — agreement, contention, attribution | `src/js/opinion_consensus.js` |
| v5.0.0 | Beemuu Platform | A | Plugin capability bridge — runner + consent UI + permission model over the shipped enforcement/library halves | `src/js/plugin_capability_bridge.js` |

**Milestone rationale.** v4.0.0 aggregates everything the app knows *per car*
into a view across *all* cars — the natural major bump after the per-car
forensics of v3. v5.0.0 completes Phase 1 of VISION.md and turns the bundled
plugin system into a shareable ecosystem, which is a platform, not a feature.

## Schedule

Cycles are ordered by dependency, not date. The v3.8–v3.9 engines are
prerequisites for the v4.x cross-signal features (a drive cycle is the unit a
fleet board summarises), and the v4.0 fleet board reuses the dossier/garage
data the v4.1 provenance pass audits. v5.0.0 is independent of the v4.x line
and could ship in parallel; it is sequenced last because it is the maximum-risk
slice (a security boundary) and benefits from a settled UI layer.

Each cycle is: engine + exhaustive unit tests + a Diagnostics/Garage panel +
`CHANGELOG.md`/`ROADMAP.md` updates + a per-cycle plan doc, then the standard
release cut (stamp → gen → test → push → tag → build → publish → deploy).

## Explicitly out of scope

- Any ECU **write** (coding, flashing, `ecu-flash`).
- The `network` and `filesystem` plugin capabilities — v5.0.0 wires the
  **read-only** capability set (`read-vin`, `read-dtc`, `subscribe-live`) and
  leaves the risky combinations to the security review in
  `docs/plugin_capability_bridge_plan.md` §8.
- A frontend framework rewrite; Rust command-surface changes
  (`src-tauri/**` is untouched by every cycle here).
