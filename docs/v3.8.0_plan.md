# Plan — v3.8.0 "Signal Integrity"

**Parent:** `docs/v3.8_to_v5.0_roadmap.md` (schedule of record)
**Tier:** A — pure analysis over a recorded log, plus a read-only panel.
**Depends on:** nothing. Every other cycle in the arc depends on *this* one.

## Why this cycle is first

The ten v3.0.0 engines each treat a channel's **values** as true. None of them
asks whether the channel itself can be believed. That ordering is backwards: a
coolant trace pinned at exactly 84.0 °C for two minutes, a lambda channel that
drops to zero for three samples, an rpm channel with a four-second hole — each
of those is a *sensor or logging fault*, and every downstream verdict built on
them reads as a real finding from the car.

So the integrity pass runs **before** the interpreters, not after.

## Slices

### S1 — `cleanPoints(points)` — *shipped*
Normalises a raw channel into something analysable and reports what it had to
throw away.
- Drops samples that cannot be represented at all (non-finite `x` or `y`).
- Sorts by `x`.
- A repeated timestamp is collapsed to its **last** read — that is the value a
  hold-last-value fallback would have produced.
- Returns `{ points, dropped, collapsed }`. `dropped` and `collapsed` are
  counted separately on purpose: a corrupted log and a coarsely timestamped one
  are different problems and the caller must be able to tell them apart.

### S2 — `analyzeChannel(name, points)` — *shipped*
Scores one channel and names what it is worried about.
- `frozen` — one constant value for the whole log (disconnected or
  default-filled sensor). Penalty **−55**: this is the failure mode that
  silently poisons every downstream engine.
- `flatline` — a long run of one repeated value inside an otherwise live trace
  (stuck sensor, hold-last-value fallback).
- `dropouts` — gaps between samples far wider than the channel's normal
  spacing.
- `steps` — implausible single-sample jumps, gated on a computed `threshold`
  rather than on robust scale, so a spike in an otherwise flat trace (scale 0,
  real range) is still caught while a constant channel and a smooth ramp are not.
- `noise` — scatter around the local trend.
- Returns `{ name, n, dropped, collapsed, span_s, unit, verdict, score,
  flatline: { frozen }, noise, steps: { count }, dropouts: { count },
  evidence }`.

### S3 — Panel — *shipped*
A Diagnostics panel that runs the integrity pass over the live/`replay` log
series and lists per-channel verdicts worst-first, each with the plain-language
`evidence` lines the engine produced. Mounts only if
`window.beeemuuSignalQuality` is present; degrades to "panel absent".

### S4 — Release cut
`stamp-release.py` → `gen-content-pages.py` → full test suite → push → tag
`v3.8.0` → CI builds and publishes → `update-on-release.yml` redeploys Pages.

## Acceptance criteria

- `node --test src/js/test/signal_quality.test.cjs` is green.
- The full suite (JS + Python) is green with the new engine in place.
- A constant channel is reported `frozen` and scores below every healthy
  channel in the same log.
- A channel with a spike in an otherwise flat trace reports a step.
- The panel shows the engine's own `evidence` strings — it does not invent
  wording of its own.
- No channel is blamed for a fault the engine did not measure.

## Non-goals

- Repairing the data. The engine reports; it never interpolates a missing
  channel and presents the result as measured.
- Any ECU interaction. This cycle reads a list of `{x, y}` points.
