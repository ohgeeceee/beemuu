# Plan — v4.1.0 "Provenance"

**Parent:** `docs/v3.8_to_v5.0_roadmap.md` (schedule of record)
**Tier:** A — pure analysis over a service history, plus a read-only panel.
**Depends on:** v4.0.0 (the fleet board grades against the history this pass
audits — a grade computed from an impossible history is worse than no grade).

## Why

The fleet board and the maintenance dossier both take a service history at face
value. A plausible-looking history is exactly the kind that is worth checking:
odometer readings that go backwards, an entry dated before the reading that
supposedly preceded it, the same service billed twice, one invoice an order of
magnitude off its neighbours.

The output has to be careful. This module can say a history contains **no
detected inconsistency**. It can never say a history is genuine, and it must
never imply that it did.

## Slices

### S1 — Findings model
Every check emits `{ kind, severity, indices, detail }` — `indices` naming the
entries involved, so the UI can point at the rows rather than hand back a
verdict from nowhere.

### S2 — The checks
- `monotonicOdometer(entries)` — a decrease is `odometer_reversal`.
- `chronological(entries)` — an entry dated before an earlier reading is
  `back_dated`.
- `duplicateEntries(entries)` — same date + odometer + items is `duplicate`.
- `costOutliers(entries)` — robust median-absolute-deviation rule, **only**
  with at least `MIN_COST_ENTRIES`; below that the check reports
  `cost_unjudged`, which is not the same as clean.
- `mileageGaps(entries)` — a gap larger than `MAX_GAP_KM` is `gap` (a stored
  car, or a cluster swap — either way the reader needs to see it).
- `implausibleIntervals(entries, now)` — an entry more than `MAX_FUTURE_DAYS`
  ahead of `now`.

### S3 — `analyze(entries, opts)`
`{ verdict: 'consistent' | 'suspect' | 'insufficient', score, confidence,
findings, summary: { n_entries, span_days, span_km, headline } }`.
`suspect` means at least one high-severity finding. `insufficient` covers the
under-quorum case below.

### S4 — Wording discipline — *tested*
The module may produce the phrase **"no inconsistency detected"**. It may not
produce `verified`, `authentic` or `genuine`, and a test asserts that no
generated `summary`/`detail` string matches `/genuine|authentic|verified/i`.

### S5 — Panel — "History provenance"
Findings list with severity, the entries involved, and the module's own detail
text. An `insufficient` history says how many entries are needed.

### S6 — Release cut (stamp → gen → test → push → tag `v4.1.0` → publish → deploy).

## Refusal contract (non-negotiable)

- Fewer than `MIN_ENTRIES` (3) entries ⇒ `verdict: "insufficient"`,
  `score: null`, `confidence: 0`, and an evidence line stating the minimum.
  A two-entry history is **not** "consistent".
- Unparseable dates and missing odometers are findings of kind `unparseable`,
  reported — never skipped, never treated as consistent.
- `now` is injected, so `implausibleIntervals` is deterministic.

## Acceptance criteria

- `node --test src/js/test/service_provenance.test.cjs` green; full suite green.
- A clean 5-entry history is `consistent` and produces zero findings.
- Each of the six check kinds fires on its own crafted history.
- A 2-entry history is `insufficient` with a stated minimum, not `consistent`.
- A low-entry-count history reports `cost_unjudged`, not a clean cost verdict.
- No output string matches `/genuine|authentic|verified/i`.

## Non-goals

- Verifying a history against an external authority. This is internal
  consistency only, and the wording says exactly that.
- OCR or invoice parsing — it consumes already-structured entries.
