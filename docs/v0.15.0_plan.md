## Premise

v0.14.0 shipped the Live Gauges panel as **sim-only** by
explicit user decision (the v0.14.2 cycle-pick
conversation, Option B). The K+DCAN cable cannot
passively listen to raw broadcast frames (FTDI firmware
terminates ISO-TP upstream), so the v0.14.0 Tier B was
gated on an OBDLink SX cable acquisition — a $50+ cable
that the user (or a community tester) would have to
acquire to ship that spine.

The DID-projection bridge the v0.14.2 plan deferred to
"v0.14.3+" is the alternative path: route the existing
`read_live_data` UDS path through to the v0.14.0 Live
Gauges panel, so the panel shows real data on the K+DCAN
cable without needing the OBDLink SX at all. v0.15.0 is
that cycle. It connects the diagnostic-protocol UDS path
to the broadcast-frame consumer in the panel, with a new
async Tauri command that drives the existing `watch_tick`
loop with a `ListenerMode::KwpDids` variant.

This is the load-bearing user-facing win of v0.15.0: an
E90 / E60 / E70 owner with the $15 K+DCAN cable can now
see the same 6-gauge Live Gauges panel (RPM, coolant, oil
temp, vehicle speed, battery voltage, throttle) that
v0.14.0's sim-only panel showed. No new hardware required.

## What this cycle ships

The cycle's spine is a 3-slice shape (mirroring the
v0.14.2 + v0.14.3 + v0.14.5 cycle patterns):

### Slice 0 — `docs(v0.15.0): cycle plan + ROADMAP header + CHANGELOG entry` (Tier A, docs only)

This PR. The cycle plan doc, the ROADMAP v0.15.0 cycle
block, the CHANGELOG `## [0.15.0] — Unreleased` section,
and the public `frontend/roadmap/v0.15.0.html` "What
shipped" / "Open questions" updates (the public page
currently claims v0.15.0 is "Next cycle. Detail to be
filled in once the plan doc lands in docs/" — this PR
fills it in).

### Slice 1 — `DID-projection bridge` (Tier A, frontend)

Maps each `[[profile.param]]` to the corresponding
`data-live-can-gauge` slot. Pure mapping logic in a new
`src/js/live_data_bridge.js` module + tests. Reuses the
v0.14.0 `can_decoders.js` for byte-level decoding when
the live-data value comes through the broadcast path.
~150 LOC + 12 unit tests (mirroring the v0.14.0
`can_decoders.js` test coverage shape).

The bridge is the consumer half of slice 3; without
slice 1, slice 3 has no frontend to push the new data
into.

### Slice 2 — `Live Gauges panel data source flip` (Tier A, frontend)

When `connected && profile selected`, the panel reads
from the bridge instead of the simulator mirror. The
sim-only fallback stays for non-connected sessions.
~50 LOC + 4 unit tests.

Slice 2 is the load-bearing user-facing change. Slice 1
is the supporting infrastructure; slice 2 is what the
user sees. The forward-roadmap doc's spine ("DID-
projection bridge + data source flip") puts slices 1 + 2
in the same Tier A batch because they're two halves of
the same frontend change.

### Slice 3 — `update_can_listen` async Tauri command (Tier B, Rust)

New Tauri command that starts / stops the existing
`watch_tick` loop with a
`ListenerMode::KwpDids { profile, interval_ms }` variant.
Different from the v0.14.0 Tier B
`ListenerMode::Simulator / OBDLinkSx` because it reads
through the diagnostic protocol, not the raw CAN bus.
~80 LOC + 3 integration tests in
`src-tauri/src/commands.rs` +
`src-tauri/tests/async_commands.rs`.

Tier B because `src-tauri/src/commands.rs` is on the
protected path. **Flag at the top of the PR body**
per CLAUDE.md golden rule #2 + the multi-writer skill's
Tier B/C gate. Human merges after the auto-merge bot's
CI gate passes.

## What this cycle does NOT ship

- ❌ No new transport support (BLE / WiFi / ENET
  auto-detect). The forward-roadmap doc's `v0.16.0`
  cycle spine ("Tier B Land Rush — BLE / WiFi / ENET")
  is the next cycle's work. ENET/DoIP auto-detect is
  preserved as a 🟡 item per the v0.14.4 / v0.14.5 /
  v0.14.6 closeout pattern.
- ❌ No `protocol/**` code changes. The
  `read_live_data` UDS path is already shipped (it's
  what the v0.14.0 Tier B uses internally). v0.15.0
  only adds the bridge + the data-source-flip in the
  frontend + the new `ListenerMode::KwpDids` variant
  on top of the existing `watch_tick` loop.
- ❌ No new crates in `src-tauri/Cargo.toml`. The
  `tauri-plugin-dialog` crate added in v0.14.1
  (PR #169) is the only new runtime crate across
  v0.14.x. v0.15.0 reuses it for the per-PID dim
  + remove UI confirmation dialog (per the
  v0.14.3 PR #190 frontend rewire pattern).
- ❌ No frontend changes that aren't pure TypeScript
  / CSS / HTML. The new `src/js/live_data_bridge.js`
  is a new JS module; the `src/css/app.css` grows a
  `.live-gauge-from-kdcan` class for the data-source
  indicator; `src/index.html` may grow a small
  toggle button for the bridge. None of these are
  new app-shell features; they're wiring.
- ❌ No community data changes (the DID-projection
  bridge works against the existing
  `community/profiles/*.toml` data shape; no
  new DIDs, no new decoders, no new profile
  entries).
- ❌ No new BMW hex descriptions.
- ❌ No `git tag v0.15.0` (Tier C release cut,
  separate step after all 3 slices land).

## Execution order

Slices 0 → 1 → 2 → 3 land in this order. Slice 0 ships
first (this PR — cycle plan + ROADMAP + CHANGELOG).
Slice 1 ships second (the bridge module + tests).
Slice 2 ships third (the data source flip in the
Live Gauges panel). Slice 3 ships fourth (the new
async Tauri command). The natural cadence is 4
sequential PRs over ~3-5 days.

The release-cut PR (the Tier C step) merges after
slice 3 lands; after that, the maintainer runs
`git tag v0.15.0 && git push --tags` to trigger
`release.yml`.

## Open questions for the maintainer

1. **Should the v0.15.0 release cut be a separate
   PR (mirror of PR #225 + #227), or skipped
   entirely?** Per CLAUDE.md golden rule #5
   ("don't let the badge lie"), the README release
   badge reflects the most recent **fully shipped**
   release. v0.15.0 is a feature cycle (DID-
   projection bridge + data source flip +
   `update_can_listen` command) so the badge
   bump is appropriate. **Default: yes**, the
   v0.15.0 release cut is a separate PR (the
   v0.14.4 / v0.14.5 / v0.14.6 release-cut
   model).
2. **Should the v0.14.6 plan doc's "Open question
   2" (the `release.yml` landing-page step
   docs change) be a separate v0.15.0 follow-up
   PR?** The v0.14.5 + v0.14.6 release runs
   (#30738207436 + #30739178321) both failed at
   the "Update beemuu.com landing page" step
   because the `BEEMUU_VPS_SSH_KEY` /
   `BEEMUU_VPS_HOST` secrets aren't configured
   in the repo. The docs change to make the
   landing-page step best-effort + document
   the secret-requirements in a new
   `docs/ops/release-yml-secrets.md` is a real
   Tier A slice. **Default: yes**, ship the
   docs change as a separate Tier A PR in
   v0.15.0 (or in v0.15.0's release cut itself).
3. **Should the v0.15.0 public landing page
   (`frontend/roadmap/v0.15.0.html`) include a
   "Preview" or "Demo" video / screenshot when
   the cycle ships?** v0.14.5's public page is
   docs-only; v0.15.0's user-facing win (real
   data on K+DCAN) is more visual. **Default: no**
   for this cycle (extra scope); a follow-on
   Tier A PR in v0.16.x can add the visual.
4. **Should the DID-projection bridge work against
   the v0.14.0 `can_decoders.js` broadcast-frame
   path AND the new `read_live_data` UDS path,
   or just the UDS path?** The forward-roadmap
   doc's "DID-projection bridge" slice description
   says "reuses the v0.14.0 `can_decoders.js` for
   byte-level decoding when the live-data value
   comes through the broadcast path" — implying
   the bridge handles both paths. **Default: both**
   (the bridge is a pure mapping function; it
   takes a value + a profile entry and returns a
   gauge slot; the source of the value is the
   caller's concern).
