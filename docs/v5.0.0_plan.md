# Plan — v5.0.0 "Beemuu Platform"

**Parent:** `docs/v3.8_to_v5.0_roadmap.md` (schedule of record)
**Tier:** A — read-only capability set, plus consent UI and docs.
**Depends on:** the shipped **enforcement half** (permission model + capability
checks) and **library half** (plugin packaging/API 2 + community registry). This
cycle is the bridge between them.
**Existing detail:** `docs/plugin_capability_bridge_plan.md`, `docs/PLUGINS.md`.

## Naming — this is not `plugin_bridge.js`

`src/js/plugin_bridge.js` already ships (PR #354) and is the **transport**: it
carries a call from a sandboxed worker out to the app and back, and has its own
15-test suite. This cycle adds the **decision layer** that transport asks, and
it lives in its own module so the shipped engine is untouched:

| Module | Job |
|--------|-----|
| `src/js/plugin_capabilities.js` | the capability table and the guarded surface |
| `src/js/plugin_bridge.js` | the transport (shipped, unchanged) |
| `src/js/plugin_capability_bridge.js` | **this cycle** — validate, classify, evaluate, prompt, audit |

## Why this is v5.0.0

`ROADMAP.md` calls the capability bridge "unbuilt work, not deferred work". It is
the single feature that turns a bundled plugin system into a platform: the
registry can *list* plugins and the permission model can *describe* what a
plugin may do, but nothing yet hands a running plugin a capability it asked for.

A major bump, not a point release, because it is a **security boundary** — the
first code in the product whose job is to say no to another piece of code.

## Slices

### S1 — Capability descriptors
Each capability is a descriptor, not a string:
`{ id, label, description, risk, readable, grantable, requires }`.
Read-only set only: `read-vin`, `read-dtc`, `subscribe-live`.
`read-vin` is marked **`sensitive: true`** and always asks, even when a broad
grant exists. `network` and `filesystem` are **not** in this cycle
(`docs/plugin_capability_bridge_plan.md` §8).

### S2 — `requestCapabilities(plugin, asked, grants)`
Pure decision function. Returns
`{ granted, denied, prompt, reasons }` where `prompt` lists exactly the
capabilities needing a human yes. Rules:
- Unknown capability ⇒ denied, with the id echoed in `reasons`.
- Already-granted and non-sensitive ⇒ granted without a prompt.
- Sensitive ⇒ always prompts, even if previously granted.
- A plugin with no declared manifest ⇒ everything denied.

### S3 — Consent model
`makeConsent(plugin, decisions, now)` → `{ plugin, at, decisions, scope }`.
Every decision is recorded with the **exact capability id** it covers — no
wildcards, no "allow all". Re-reading a consent record that names a capability
the plugin never asked for is itself a reported inconsistency.

### S4 — `guardCall(plugin, capabilityId, consent)`
The runtime gate a bridged call passes through:
`{ allowed, reason }`. Denies when the capability was never consented, when the
consent is for another plugin, and when the capability is unknown. This is the
only place a call is allowed or refused, so there is one place to test.

### S5 — `revoke(consent, capabilityId, now)`
Revocation is a first-class operation with its own recorded timestamp, and it
works on a single capability without touching the others.

### S6 — Consent panel
Per plugin: requested capabilities, risk, what is granted, and Revoke per row.
A sensitive capability is visually and textually distinguished from a read-only
one — not by colour alone.

### S7 — Docs
`docs/PLUGINS.md` gains a "Capability bridge" section written from the shipped
code, and `docs/plugin_capability_bridge_plan.md` gets a status header marking
which sections are now implemented and which remain (§8 security review).

### S8 — Release cut (stamp → gen → test → push → tag `v5.0.0` → publish → deploy).

## Refusal contract (non-negotiable)

- Default deny. Anything not explicitly granted and consented is refused with a
  named reason.
- No wildcard grants, ever, and a test asserts a `"*"` capability id is denied
  and echoed as unknown.
- A consent record can never be extended by reading it — `guardCall` is pure
  and takes the consent as an argument.
- No capability in this cycle can write anything.

## Acceptance criteria

- `node --test src/js/test/plugin_capability_bridge.test.cjs` green; full suite green.
- Default deny: an empty grant set denies everything.
- A sensitive capability prompts even when already granted.
- `guardCall` refuses a consent issued to a different plugin.
- `revoke` removes exactly one capability and leaves the rest intact.
- `"*"` is denied as unknown.
- The panel renders a sensitive capability as distinguishable without relying
  on colour.
- `docs/PLUGINS.md` documents the shipped behaviour, not the intended one.

## Non-goals

- The §8 security review itself, and any network/filesystem capability.
- Loading or executing third-party plugin code in-process. The bridge decides
  and logs; execution remains where it already is.
