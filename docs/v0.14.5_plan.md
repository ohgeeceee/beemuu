## Premise

v0.14.4 was a "ship what we promised, harden what we shipped"
cycle: it closed the test-coverage gap on the diagnostic-story
+ secure-snapshot features, refreshed the stale CLAUDE.md
invariants, audited the ROADMAP v0.3.0 historical section, and
fixed the missing Tauri Linux system dependencies in
`ci.yml::test-rust`. None of those slices moved the public
surface.

v0.14.5 is the cycle that **opens the project further** to the
E-series owners the v0.14.2 / v0.14.3 cycles explicitly
deferred. v0.14.2 / v0.14.3 / v0.14.4 worked the N62 / E70
chassis end-to-end (oil temp, fuel rate, engine runtime,
harness doc, per-PID NRC + remove-from-profile UI, test
coverage on the user-facing story + anonymize paths). v0.14.5
generalises that work to the **N52 / N54** E-series family
that the existing community profiles already cover but that
the v0.14.2 cycle explicitly deferred to "the next cycle after
N62 wraps up."

The cycle name **"Open & Committed"** matches the public
`frontend/roadmap/v0.14.5.html` tagline published in PR #221
and reflects two commitments:

1. **Open** the codebase to more E-series engines — N52 and
   N54 get the same OBD-II PID enrichment the N62 received
   in v0.14.2 + v0.14.3 (`0x5C` oil-temp swap, three new
   fuel-rate / runtime PIDs), plus the per-chassis harness
   doc an E90 / E60 owner can run on a real car.
2. **Committed** to the discipline that keeps the public
   surface honest — every new PID carries the
   `[needs verification, N5x/E9x bench]` marker until a
   real-car report lands; every cycle closes with a doc
   audit; every Tier A surface ships under the
   `tests/async_commands.rs` allowlist guard without
   regressions.

## What this cycle ships

The cycle's spine is a 3-PR shape mirroring the v0.14.2 +
v0.14.3 + v0.14.4 pattern (plan + data + harness doc + cycle
closeout). All slices are Tier A docs + community data — no
`transport/**`, no `protocol/**`, no `commands.rs`, no
protected paths. The v0.14.5 release cut (version bumps, git
tag, installer build, landing-page deploy) is Tier C and
follows slice 3.

### Slice 0 — `docs/v0.14.5_plan.md` + ROADMAP v0.14.5 header (this PR, Tier A, docs only)

Pure docs. Adds the cycle plan doc (this file), inserts the
v0.14.5 cycle block at the bottom of `ROADMAP.md` after the
v0.14.4 cycle block, and adds an Unreleased v0.14.5 section
to `CHANGELOG.md` per the established v0.14.x convention. The
`docs/forward_roadmap_14.4_to_16.9.md` doc's v0.14.5 candidate
list is the upstream source for this cycle's slice selection.

### Slice 1 — `community/profiles/n52.toml` + `community/profiles/n54.toml` enrichment (Tier A, data only)

Mirrors the v0.14.2 N62 slice 1 (`0x5C` oil-temp swap, PR
#175) and the v0.14.3 N62 slice 2 (three new PIDs, PR #186).

- **`n52.toml`** — replace the `local:10` oil-temp placeholder
  (labelled `[UNVERIFIED placeholder]`) with the standard
  OBD-II PID `0x5C` (engine oil temperature, `byte - 40 °C`,
  decoder `temp_u8`). Add the three v0.14.3 N62 PIDs:
  - `0x5E` — engine fuel rate L/h, `u16_fiftieths` decoder
    (idle ~1–2 L/h, WOT ~50–90 L/h).
  - `0x5F` — engine runtime since start, `u32_be` decoder
    (4-byte BE seconds; `0xFFFFFFFF` overflow sentinel).
  - `0x62` — engine fuel rate g/s, `u16_half` decoder
    (idle ~1–2 g/s, WOT ~40–70 g/s; load-bearing for BSFC).
  Each new entry carries the
  `[needs verification, N52/E9x bench]` marker, matching
  the v0.14.3 N62 discipline. The N52 instrumentation-context
  header block grows with the BSD oil-condition sensor note
  (N52's known oil-temp quirk: the DME reads oil condition
  via BSD, not KWP2000).
- **`n54.toml`** — same four-entry enrichment as N52 plus the
  N54-specific instrumentation context: charge-air
  temperature note (N54 IAT reads post-intercooler, so
  heat-soak is the load-bearing observation), HPFP rail
  pressure (the existing `0x23` entry stays; v0.14.5 doesn't
  add to it), and the "stock peak ~60–70 kPa over baro"
  boost note.
- **No new decoders** — all four OBD-II PIDs reuse
  `temp_u8`, `u16_fiftieths`, `u32_be`, and `u16_half`,
  which shipped in v0.14.3 PR #185.
- **Profile label** — both `n52.toml` and `n54.toml` lose
  the `[community, oil temp unverified]` mark from their
  `label` field once `0x5C` is in. The label still carries
  `[community]` (the conservative-sourcing marker that
  applies to the whole profile until a real-car
  verification report lifts it).

### Slice 2 — `docs/validation/n5x-real-car.md` harness doc (Tier A, docs only)

Mirrors the v0.14.2 N62 harness doc (`docs/validation/
n62-real-car.md`, PR #178) and the v0.14.3 N62 extension
(`docs/validation/n62-real-car.md` Step 2–5, PR #188). The
N5x doc covers:

- **Wire-up** — K+DCAN cable on E9x 325i / 328i / 330i (N52)
  or E9x 335i / E60 535i / E89 Z4 35i (N54). The K+DCAN
  cable cannot passively listen to raw broadcast frames
  (FTDI firmware terminates ISO-TP upstream); the
  `read_live_data` Tauri command is what reads each
  `[[profile.param]]`, same as the N62 harness.
- **Cold readings** — Step 2 table for the 13 PID entries
  the N52 / N54 profiles will ship after slice 1 (8 existing
  OBD-II PIDs + 4 new v0.14.5 PIDs + 1 future UDS-only
  entry). Critical row is oil temp (the `0x5C` swap is the
  gating change) and fuel rate (the three new PIDs the
  v0.14.3 cycle added to N62 are the gating change here).
- **Running readings** — Step 3 table. N52 idle load is
  15–25 % (Valvetronic idle, mirror of N62); N54 idle load
  is 18–30 % (twin-turbo, less valve lift at idle). N54
  cruise rail pressure is 5,000–20,000 kPa depending on
  load; failing HPFP shows as pressure collapsing under
  demand.
- **Report template** — Step 4 markdown block. Mirrors the
  N62 report template; fields specific to N52 / N54 are
  the chassis + firmware (MSV70 / MSV80 for N52; MSD80 /
  MSD81 for N54), the BSD oil-condition sensor note for
  N52, and the rail-pressure-collapse observation for N54.
- **What we will do with the report** — Step 5 closes
  with: a passing report removes the `[needs verification,
  N5x/E9x bench]` labels from all four v0.14.5 PIDs;
  a failing report reverts the enrichment for that PID
  only (the corresponding `[[profile.param]]` entry is
  removed or, for `0x5C`, restored to the `local:10`
  placeholder with the `[UNVERIFIED placeholder]` tag).

The harness doc lands **after** slice 1 because it lists the
exact PID values the slice 1 entries will populate. Reversing
the order would put the doc ahead of the data.

## What this cycle does NOT ship

- ❌ **No `transport/**` code changes.** The K+DCAN / ENET /
  DoIP paths are not touched. The forward-roadmap doc's
  Tier B candidate for v0.14.5 (ENET/DoIP UDP broadcast
  discovery) is preserved as a 🟡 item deferred to v0.15.0+
  per the forward-roadmap's `v0.16.0` cycle spine (BLE /
  WiFi / ENET land rush). ENET/DoIP discovery is the
  highest-leverage Tier B work; it stays Tier B because
  it touches `transport/` and `commands.rs` and needs a
  real-car test.
- ❌ **No `protocol/**` code changes.**
- ❌ **No frontend changes** (no `src/js/**`, no
  `src/css/**`, no `src/index.html`).
- ❌ **No `commands.rs` changes.**
- ❌ **No new crates** in `src-tauri/Cargo.toml`. The four
  decoders the slice 1 PIDs use are already shipped
  (`temp_u8` is the existing `temp_u8` decode; `u16_fiftieths`
  / `u32_be` / `u16_half` shipped in v0.14.3 PR #185).
- ❌ **No `git tag v0.14.5`.** That's the Tier C release
  cut, the next step after the cycle's three PRs land.
- ❌ **No new BMW hex descriptions** added to the codebase.
  Per the v0.14.3 PR #186 source-policy precedent, the
  four v0.14.5 PIDs are SAE J1979 emissions-mandated and
  sourced from the published standard, not from forum
  threads. The `verified` confidence comes from the SAE
  J2012 standard; the `community` confidence applies to
  the N5x-specific application until a real-car report
  upgrades it.

## Execution order

Slices 0, 1, and 2 are sequential: 0 lands first (the plan
doc), 1 lands second (the data), 2 lands third (the harness
doc that references the slice 1 PID values). The natural
cadence is 3 sequential PRs over ~2–3 hours.

The release-cut PR (the Tier C step) merges after slice 2
lands; after that, the maintainer runs
`git tag v0.14.5 && git push --tags` to trigger
`release.yml`.

## Open question for the maintainer

1. **Does the N52 oil-condition sensor (BSD, not KWP2000)
   need a separate harness step?** N52 oil temperature is
   primarily communicated via the BSD (Bit Serial Data)
   protocol from the oil condition sensor to the DME, not
   over KWP2000 — the existing `local:10` placeholder was
   a guess that the OBD-II path would work, and the
   forward-roadmap doc's v0.14.5 candidate list flags this
   as a known issue. The slice 2 harness doc covers the
   OBD-II `0x5C` swap verification; if the BSD path is
   what the N52 DME actually uses, the slice 1 enrichment
   is wrong (the DME won't respond to `0x5C` on N52). The
   expected outcome: the bench verification on an E90 N52
   surfaces an NRC for `0x5C` (the `tests/async_commands.rs`
   per-PID NRC error surface from v0.14.3 PR #187 is what
   surfaces it in the UI), and the slice 1 entry is
   removed or marked `[UNVERIFIED placeholder]` per the
   `n5x-real-car.md` Step 5 protocol. **Default: ship the
   enrichment with the `[needs verification]` marker and
   let the harness report decide** — that's what the
   marker discipline is for.

2. **Should the `community` confidence label on N52 / N54
   be downgraded to `unverified` until the harness doc
   lifts it?** The forward-roadmap doc's v0.14.5 slice 1
   doesn't change the profile `label` field's `[community]`
   tag, but the v0.14.4 PR #215 confidence taxonomy
   (applied in PR #215's `confidence: "verified" |
   "community" | "unverified"` column on the backend
   `dtc` table) could be applied to the profile TOML
   `label` field too. **Default: leave the `label` field
   as `[community]`** — the existing label discipline is
   the right level of granularity for the TOML
   `community/profiles/` knowledge base, and the
   per-PID `[needs verification]` markers are the
   fine-grained signal.
