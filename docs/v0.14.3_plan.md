# BeeEmUu v0.14.3 — Cycle Plan

> **Status:** v0.14.2 cycle closed 2026-07-29 (PRs #171, #175,
> #177, #178). This doc is the proposed v0.14.3 cycle shape, ready
> for the maintainer's review. Per `COMMUNITY_FRAMEWORK.md`'s
> "no feature without a Discussion" rule, **no v0.14.3 work should
> land before a Discussion thread opens on the repo.** This doc is
> the seed for that discussion, not a substitute for it.

## Premise

v0.14.2 deliberately narrowed the N62 / E70 enrichment to a single
new OBD-II PID (`0x5C` engine oil temperature) and explicitly
deferred three more PIDs (`0x5E` engine fuel rate L/h, `0x5F`
engine runtime sec, `0x62` engine fuel rate g/s) **because each
needs a new decoder that does not yet exist in the catalog**.
Shipping a profile entry that references a non-existent decoder
breaks every consumer at load time with `unknown decode: X`, so
the **decoder-first discipline is preserved**. PR #175's
description spells this out.

v0.14.3 picks the cycle name **"Finish the Bench"** because the
work is about completing the v0.14.2 premise: every PID the
slice 3 harness doc asks the user to verify is in the profile,
with the decoders it needs, and the per-PID NRC error surface the
slice 2 UI deferred to v0.14.3 is also in place.

This is the **narrowest defensible scope** consistent with the
multi-PR shape of the v0.12.0 / v0.13.0 / v0.14.0 / v0.14.2
cycles. Each item is small, well-bounded, and ships
independently. Nothing in this plan is a blocker for any other
item. Tier split: 2 Tier A slices (data + frontend), 1 Tier B
slice (protocol), 1 docs-only slice.

## What this cycle ships

### Slice 1 — `u16_fiftieths` / `u32_be` / `u16_half` decoders (Tier A, Rust only)

The three decoders the v0.14.2 slice 1 PR explicitly cited as
missing:

| Decoder | Input | Formula | Output | PIDs that need it |
|---|---|---|---|---|
| `u16_fiftieths` | 2 bytes BE | `raw × 0.02` | `f64` | OBD `0x5E` engine fuel rate (L/h) |
| `u32_be` | 4 bytes BE | `raw as f64` | `f64` | OBD `0x5F` engine runtime (sec since start) |
| `u16_half` | 2 bytes BE | `raw × 0.5` | `f64` | OBD `0x62` engine fuel rate (g/s) |

Each follows the existing pattern in
`src-tauri/src/data/live.rs`: a new `Decode` variant, a new arm
in the `decode()` match, a new arm in `decode_from_str` +
`decode_to_str`, a new spec section in
`docs/DECODE_FUNCTIONS.md`, and 3-4 unit tests in the existing
`#[cfg(test)] mod tests` block at the bottom of `live.rs`.

Three new decoders in one slice is at the upper end of what a
single PR can carry, but the test surface is uniform and the
code change per decoder is ~20 lines. If the maintainer wants a
tighter slice 1, the split is: 1a) `u16_fiftieths` + `u32_be`
(for `0x5E` + `0x5F` — the two fuel-rate and runtime PIDs that
don't share an encoding), 1b) `u16_half` (for `0x62` — the
g/s fuel rate). The 1a/1b split is documented in the
"Open question" section below.

### Slice 2 — Re-enable the deferred N62 PIDs (Tier A, data only)

With the three new decoders in the catalog, the three deferred
profile entries in `community/profiles/n62.toml` can ship:

```toml
[[profile.param]]
id = "fuel_rate_lh"
label = "Engine fuel rate (L/h)"
unit = "L/h"
query = "obd:5E"
decode = "u16_fiftieths"
min = 0.0
max = 100.0

[[profile.param]]
id = "engine_runtime"
label = "Engine runtime"
unit = "s"
query = "obd:5F"
decode = "u32_be"
min = 0.0
max = 4294967295.0

[[profile.param]]
id = "fuel_rate_gs"
label = "Engine fuel rate (g/s)"
unit = "g/s"
query = "obd:62"
decode = "u16_half"
min = 0.0
max = 100.0
```

Each entry carries an evidence marker per `docs/DECODE_FUNCTIONS.md`'s
data-discipline convention. The slice 3 harness doc (PR #178) is
the verification path — the `Step 2` cold reading table in that
doc grows three rows for the new PIDs.

### Slice 3 — Per-PID NRC dim + remove-from-profile UI (Tier B, frontend + protocol)

The v0.14.2 slice 2 PR (#177) shipped the `parseNrcError` +
`isUnsupportedNrc` helpers and the friendly log line, but
**deferred the per-PID dim + remove UI** because the current
`read_live_data` Tauri error string surfaces the (sid, nrc) pair
but **not the DID** that was rejected. A clean per-PID UX needs
the protocol layer to surface the DID in the error.

This slice threads the DID through `src-tauri/src/protocol/mod.rs`'s
NRC error string and re-enables the `addUnsupportedPid` /
`removeUnsupportedPid` helpers in `main.js` (already drafted in
the v0.14.2 slice 2 PR, removed before merge because there was
no DID to bind them to). New Tauri commands: `remove_profile_pid`
(profile TOML edit, gated behind a confirmation dialog per
`docs/CONTRIBUTING.md`'s write-path discipline).

Tier B because the slice touches `src-tauri/src/protocol/**` and
adds a new Tauri command to `src-tauri/src/commands.rs`. The
async_commands allowlist guard (`tests/async_commands.rs`) will
need the new command to be `async` + `spawn_blocking` if it does
file I/O.

### Slice 4 — `docs/validation/n62-real-car.md` extension + ROADMAP cycle closeout (Tier A, docs only)

Adds the three new PIDs to the Step 2 + Step 3 cold / running
reading tables in the slice 3 harness doc (PR #178). Marks the
v0.14.3 cycle table in `ROADMAP.md` as `✅ Done` for all four
slices. Updates the "Last updated" header line.

## What we will NOT do (this cycle)

- **Touch `transport/**`.** No new transport module. The K+DCAN
  cable continues to drive the existing `read_live_data` path.
  The v0.14.0 Tier B (raw-CAN listener + `get_latest_can_frames`)
  remains gated behind OBDLink SX acquisition.
- **Add a new crate.** All three new decoders are
  2-byte / 4-byte BE shifts and divides — no `byteorder` /
  `num-traits` / `binrw` needed. The existing `decode()` match
  already does this for `u16_quarter` and friends.
- **Modify the v0.14.0 Live Gauges panel.** The user explicitly
  opted to leave it as sim-only (per the v0.14.2 cycle-pick
  conversation, Option B). Same constraint applies here.
- **Cut a release tag.** Tier C, requires the maintainer's call.

list. The v0.14.3 release cut is a separate Tier C step
following slice 4.

## Execution order

Slices 1 and 3 are independent of each other but slice 2 depends
on slice 1 (the decoders must exist before the profile entries
that reference them can ship), and slice 4 depends on all three
(it extends the harness doc with the new PIDs and closes the
cycle table). The natural cadence is 1 → 2 → 3 → 4 in four
sequential PRs over 3-5 days. Slices 1 and 3 can parallelise
across two clones if the maintainer wants to land them in the
same window.

## Open question for the maintainer

1. **One PR for all three decoders, or 1a/1b split?** The
   three decoders in one PR is at the upper end of what fits
   cleanly in a single review pass. The 1a/1b split is one
   extra day of overhead but each PR is ~60 lines of Rust
   plus tests. **Default: one PR.** The 1a/1b split is the
   fallback if review feedback wants smaller PRs.

2. **Re-enable the orphaned `live-unsupported` DOM from the
   slice 2 WIP?** The DOM block + the `addUnsupportedPid` /
   `removeUnsupportedPid` helpers were drafted in the slice 2
   PR (#177) but removed before merge because the protocol
   layer didn't surface the DID. Slice 3 of this cycle is the
   natural place to bring them back. **Default: yes, as part
   of slice 3.**

3. **Does the `remove_profile_pid` Tauri command belong in
   this cycle, or v0.14.4?** The user-facing "remove from
   profile" affordance is half-useful without it (the PID is
   dimmed and one-click-removed from the *current session*,
   but the profile TOML is unchanged — the PID comes back on
   the next profile load). The command is a small Tier B
   addition but it's the difference between "looks nice" and
   "actually does the thing the user clicked." **Default:
   include it in slice 3** — without the command, the
   one-click remove button is misleading.
